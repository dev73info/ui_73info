## 一、三层结构

```
src/styles/tokens.css     令牌层    唯一的色值来源
src/primitives/           行为层    定位引擎、浮层开合、列表导航、焦点陷阱、关闭行为、滚动锁定、稳定 id（无样式）
src/components/           组件层    只消费令牌，禁止写裸色值
```

分层的**唯一目的**是那第四条约束：**组件层不许出现裸色值**。

`user_client` 的现状是 3666 处颜色字面量对 925 处令牌引用（约 4:1）。数字说明问题不在
「组件库好不好换」，而在颜色没有归属：改一次主色要人肉找出该改的那几百处。
建了第三层之后，新代码在结构上就没有写死颜色的位置——这是本库存在的理由，
其余设计都是为它服务的。

行为层单独拆出来的理由不同：焦点陷阱、Esc/点外部关闭、滚动锁定这三件事与视觉无关，
下拉、气泡、日期面板、弹窗要的是**同一套**。写在组件里就会复制四遍，且四遍的
边界条件会各不相同。

第二批组件（下拉、气泡、日期面板、选择器）把这条理由用满了：它们共用**定位引擎**
（锚点+面板、翻转、收拢、滚动跟随）与**开合行为**（四种触发方式、Esc、点外部），
除了 `useFloating` 与 `useOverlay` 两处，每个组件自己只需要关心「面板里有什么」。
写这七个组件时，浮层相关的代码一行都没有重复。

## 二、令牌层与主题模型

### 两套主题，一套词汇

`user_client` 一个 SPA 里并存两套视觉体系（门户 / 开发者），本库把它们建模成两个**主题**：
同名令牌取不同值，组件只认 `--73-*`，不关心自己在哪套主题下。

| 主题 | 什么时候用 | 主色 | 状态色 |
| --- | --- | --- | --- |
| `portal`（默认，声明在 `:root`） | 首页、需求大厅、资源、社区、个人中心、工作台外壳 | `#1f4ad1` | 绿 `#16805c` / 琥珀 `#d97706` / 红 `#b42318` |
| `dev` | 开发者工作台、资源管理、需求详情、钱包 | `#1f4ad1` | 青 `#2aa6a4` / 金 `#b9812b` / 红 `#dc2626` |

### 为什么只有两个主题（以及工作台外壳为什么不是第三个）

门户工作台外壳看着像第三套：它有自己一整套 `--wb-*`（`portal-workbench.css`），
取值还和 `--dev-*` 逐项相同。但它**不是一套完整色板，也不是一个主题**，三条理由：

1. **它只定义了 10 个令牌**：4 个尺寸（卡片 24 / 内嵌块 12 / 控件 10 / 控件高 36）
   + 主色三件套（accent / accent-soft / accent-line）+ 描边 + 弱化墨色 + 阴影。
   **没有背景、没有表面、没有正文墨色、没有弱化文字、没有状态色**——那些沿用门户侧
   与 `profile.css` 的 `--profile-*`。拿它当主题，等于只有 6 个颜色有值。
2. **它的状态色跟随当前模式。** 门户模式下 `.profile-page` 与 `.wb-dialog`
   把 Element 的成功/警示映射到门户的绿 `#166534` 与琥珀 `#92400e`；
   开发者模式下 `.user-workbench--dev` 与 `.dev-dialog` 映射到青与金。
   同一张页面切一次模式就换一套状态色。
3. **代码里直接印证了这个模型**：`MessagesView.vue`、`NotificationCenterView.vue`
   这类「两个工作台共用一页」的页面，按模式在
   `page-shell … profile-page`（门户体系）与 `dev-page`（开发者体系）之间切根类
   ——它们选的是两个主题之一，不存在第三种。

所以工作台外壳的正确定位是**「当前是哪个模式就用哪套主题」**。它之所以在两种模式下
看着一样，是因为那 10 个结构值当初被刻意冻结成了 dev 的取值（源文件注释：
「同一套菜单在两种模式下被来回切换……必须长得一模一样，否则切一次模式就像换了个网站」）。

**如果把它做成第三个可选主题会直接渲染错**：门户模式下的工作台显示绿与琥珀，
而 `workbench` 会把状态色解析成 dev 的青与金。顺带一提，只把它当「`dev` 的别名」
也不行——它少的那几档（背景、表面、正文墨色）会全部取 dev 的值，而真实的
门户模式工作台取的是门户与 profile 的值。

**将来迁移那个外壳时要处理的事**（现在不做，因为还没有迁过来的外壳可对着看）：
它那 10 个结构值需要与门户侧略有差异（例如 `--wb-ink-soft` 是 `#475569`，
门户侧 `--73-ink-soft` 是 `#52627a`；描边与阴影也不同），而外壳又要求在两种模式下
保持一致。这需要「结构值冻结 + 状态色跟随模式」的表达方式，不是加一个主题名能解决的。
`alias.css` 因此**不桥接 `--wb-*`**，理由写在该文件顶部。

### 两个不在主题层里的令牌组

| 令牌组 | 为什么不在主题层 |
| --- | --- |
| `--profile-*`（`profile.css` 的 `.profile-page`，强调色 `#4f8cff`） | 《设计规范》明确它只在 `.profile-page` 内生效、不作为全局令牌，是**页面级**色板 |
| `--wb-*`（`portal-workbench.css`） | 见上一节：它是外壳被冻结的结构值，跟随主题反而会让两种模式分叉 |

### 色值全部照搬，没有重新设计

`tokens.css` 里每一个值都能追到源文件：门户侧来自 `resource-core.css` 的 `:root`、
`home.css` 的 `.portal-home`、`profile.css` 的状态色对；开发者侧来自 `dev-base.css` 的
`:root`。

有条一律的做法值得说明：**源文件没登记过的档位用 `color-mix()` 从已有基色算**，
而不是新写一个字面量。例如状态色的描边（`--73-success-line`）都是「基色 32% 透明度」，
用的是与 `--73-accent-line` 同一个 alpha。这样换基色时描边自动跟着走，
也不会因为「要给每支状态补一条描边」而多出六个谁都不记得来源的十六进制。
`color-mix` 在这个仓库里已有先例（`home.css`、`rich-text-code.css`、`DevHomeView.vue`）。

### 切主题

```html
<html data-73-theme="dev">
```

纯 CSS，没有 JS 重算、没有重新注入样式表。`applyTheme()`（`src/theme/index.ts`）只是
封装了「写属性 + 同步响应式镜像」这一件事。

**一个必须记住的 CSS 事实**：自定义属性在**声明它的那个元素**上求值，后代继承的是
已经算好的结果。所以：

- 新组件读 `var(--73-*)`，把主题属性挂到任意子树都能让那棵子树换主题；
- 但 `alias.css` 要映射的旧变量名广泛用于 `:root` 作用域，**只有把主题属性挂在 `<html>` 上**
  兼容层才正确。

理论位置：`rootElement()` 在 `src/theme/index.ts`，实现细节见 `tokens.css` 顶部注释。

## 三、兼容层 `alias.css`

迁移期的临时桥：把 `--dev-*` / `--accent` / `--portal-*` 这些旧名字
指向 `--73-*`。那些还没搬走的手写样式因此继续工作，而值的来源已经统一到一处。

**它不是自动引入的**（不在 `styles.css` 里），因为它有三个前置条件，缺一个就会出事：

1. **必须在 `<html>` 上有 `data-73-theme`。** 否则桥接不生效（原因见上一节）。
2. **没准备好迁移就不要引。** `--73-*` 的默认主题是 `portal`；引了但没挂主题属性，
   `--dev-*` 会被解析成门户侧的色值，**开发者页面整片变色**。没引的时候
   `--dev-*` 仍由 `user_client` 自己的 `dev-base.css` 提供，一切照旧。
3. **`--profile-*` 与 `--wb-*` 不在桥接范围内。** 前者是页面级色板；后者是工作台外壳
   被冻结的结构值，桥接到主题就变成主题相关，将来 `--73-border` 一改，外壳的描边
   只在 `dev` 模式下跟着变、`portal` 模式下不变，两种模式就分叉了。
   它继续由 `portal-workbench.css` 的 `:root` 提供。

整个文件在迁移完成后应当删除。**`user_client` 的迁移已于 2026-10-01 完成，而这个文件
自始至终没有被引过**——页面在逐页迁移里直接改用了 `--73-*`，没有走「旧名换新名」那条
全局路径。所以它现在没有任何使用者，按计划可以删掉（连同 `package.json` 里的
`./alias.css` 出口）；先留着是因为它把「为什么不能提前引」写清楚了，
下一个宿主迁移前值得读一遍。

## 四、行为原语层

零第三方依赖意味着这部分也要自己写。七条经验写在代码注释里，这里列结论：

| 原语 | 关键点 |
| --- | --- |
| `useFloating` | **定位引擎**。`position: fixed` + 视口坐标（不必知道滚动容器是谁，也不会被祖先的 `transform` 带跑）；主轴翻转、交叉轴收拢；`ResizeObserver` 盯面板与内容，否则异步填进来的列表会把面板底部压到视口外 |
| `useOverlay` | **开合**。四种触发方式（click / hover / focus / manual）、受控与非受控、悬停延迟；把上面两个原语与 `useDismissable` 串起来 |
| `useListbox` | **列表键盘导航**。高亮用 id 而不是下标；项自注册，`v-if` 摘掉的项自动退出序列；↑↓ 循环、Home/End、typeahead、跳过禁用项 |
| `useFocusTrap` | 可聚焦元素要**过滤可见性**（`display:none` / `hidden` / `inert` 子树会让 Tab 在看不见的位置空转）；容器内没有可聚焦元素时要把焦点留在容器上，不能放行；关闭后焦点要还给打开前的元素 |
| `useDismissable` | 多层同时打开时**只有最上面那层**响应 Esc 与点外部，否则一次 Esc 关掉三层；监听用 `pointerdown` 的捕获阶段，避免「关闭了又触发一次打开」的双跳 |
| `useBodyScrollLock` | 要**引用计数**（两层弹窗叠着时第一层关闭不能解锁）；`overflow:hidden` 会让滚动条消失、内容右移，要补等宽 `padding-right` |
| `useId` | 直接用 Vue 3.5 内置的，不自己造计数器版本——自造的会撞 SSR 水合不匹配 |

`useDismissable` 的 `ignore` 选项容易被忽略但它很关键：`Teleport` 到 `body` 的面板、
以及触发本层的按钮，都不在容器 DOM 子树里，不声明它们就会出现「点面板自己就关了」
和「点触发器没反应」。浮层族的触发器和面板**都**要声明进去。

### 三个原语串起来的样子

```
useFloating  ── 面板贴在哪、放不下往哪翻、滚动时怎么跟
useDismissable ─ 什么时候该关（Esc / 点外部 / 层栈）
useOverlay   ── 把上面两个 + 四种触发方式 + 受控模式合成一个 useOverlay()
```

`TSelect` / `TDropdown` / `TTooltip` / `TPopover` / `TDatePicker` 都只写
`useOverlay({ trigger, placement, … })` 一行，再各写自己的面板内容。
选择器与菜单另外再叠一层 `useListbox`（键盘高亮）。

### 两个必须踩过才知道的坑

**受控判断必须动态。** `useOverlay` 支持受控（`v-model:open`）与非受控两种用法，
判据是「`open` 这个选项当前有没有值」而不是「有没有传 `open` 选项」。
`TTooltip` / `TPopover` 为了两种用法都能用，传的是一个
`props.open === undefined ? undefined : props.open` 的 getter；
若在 setup 里判一次「传了就是受控」，没绑 `v-model:open` 时也会被当成受控，
`show()` 只发一个 `update:open` 出去、自己永不打开——表现是「提示和气泡点了没反应」。

**`Ref` 不能放进响应式数组里传。** `TTable` 的列注册表是 `ref<RegisteredColumn[]>`，
而 `ref()` 会做深度代理，访问时把嵌套的 `Ref` **解包成它的值**：类型上说是 `Ref`、
运行时拿到的是 `number`。所以「拖动后的列宽」用一对取值 / 写值函数传递，
不用 `Ref`——函数本身不会被代理改写，而函数体里读的那个 `Ref` 照样被追踪，
响应式一点没丢。

prop 与 `TForm` 的整表 `size`，没有 locale 层）。两处的账见第八节。

### 两个轴：`variant`（形状）× `tone`（语义色）

不采用单轴枚举，因为迁移时遇到的组合（`el-button type="success" plain` 这类）
单轴表达不了。`tone` 只接受语义（`accent` / `success` / `warning` / `danger` / `info` /
`neutral`），不接受色值——接受色值就等于又开出一条写死颜色的路。

| 旧写法 | 新写法 |
| --- | --- |
| `.dev-btn--primary` | `variant="solid" tone="accent"` |
| `.dev-btn--ghost` | `variant="outline"`（默认，`tone` 默认 `neutral`） |
| `.dev-btn--gold` | `variant="solid" tone="warning"` |
| `.dev-btn--danger` | `variant="outline" tone="danger"` |
| `el-button type="primary"` | `variant="solid" tone="accent"` |
| `el-button plain` | `variant="outline"` |
| `el-button link` / `text` | `variant="text"` |

注意 `success` 与 `warning` 在两套主题下**不是同一个颜色族**：开发者侧的「成功」是青、
「警示」是金，门户侧是绿与琥珀。这正是主题该干的事，调用方只管写语义。

### 类名约定

每个组件的**根元素**带两个类：自己的名字 + 公共的 `t73`，例如
`<button class="t73-button t73">`、`<div class="t73-dialog t73">`。

`reset.css` 的所有规则都挂在 `:where(.t73 …)` 下，`:where()` 优先级为 0，
所以组件自己的样式永远能覆盖底座，不需要 `!important`。公共的 `t73` 类只负责
排版基线（字体族、字号、行高、墨色）与 `box-sizing`——**字体与墨色必须由组件自己声明**，
不能继承宿主 `body`：门户与开发者两套主题的字体、墨色不同，而
`resource-core.css` 的 `body { color: var(--text-main) }`（门户墨色 `#172033`）
确实会盖到开发者页面上。

### 过渡期的一处刻意统一

卡片圆角在 `user_client` 现状里有 16px / 18px / 22px / 24px 四种，`TCard` 只认
`--73-radius-card`（24px）。门户侧的卡片会因此比原来圆一点——这是收敛，不是漏改。
同类收敛还有弹窗圆角（22 / 18 / 8 三种收成 `--73-radius-dialog` 18px）。

### 命令式 API 的容器归谁持有

`TMessage` / `TMessageBox` 没有模板可挂，所以要先回答「容器从哪来」。答案是：
**第一次调用时才建容器，之后复用**。

- 容器是一个 `document.createElement('div')` 追加到 `body`，再交给 `createApp` 挂载；
- 提示用一份 `reactive` 数组驱动（列表组件直接读它，改了就会重渲染），
  所以**只挂一次应用**，不是每弹一条提示就 `createApp` 一遍；
- 容器与应用的引用留在模块作用域里，进程级单例；
- SSR（`typeof document === 'undefined'`）下所有入口直接返回空句柄，不抛错。

提示与确认框是**两套运行时**：提示可以同时存在多条（堆叠，上限 5 条，超出挤掉最旧的），
确认框是模态的、一次只能有一个，所以它带一个**队列**——前一个还没关就再调 `confirm`
会排队，而不是叠上去。确认框的渲染层直接复用 `TDialog`，
焦点陷阱 / Esc / 滚动锁定这三件事因此不必重写一遍。

确认框返回的是 `Promise<boolean>`（`confirm`）或 `Promise<void>`（`alert`），
在 `finish()` 里先收起、再取走回调、最后才通知调用方——调用方在回调里常常会立刻
再弹一个框，顺序反了就会两个框叠在一起。

### 提示条的样子来自宿主既有的 toast

`TMessage` 的视觉不是新设计的，是**对着 `user_client` 已有的那条 toast 做的**
（`src/components/AppToast.vue` + `src/styles/toast.css`）：右下角、半透明语气色块
＋ 同色描边、粗体文案、常驻 `×`；窄屏（≤640px）挪到顶部通栏并把进场方向换成自上而下。
这样宿主那 55 个文件从 `showToast` 换到 `TMessage` 时，看到的是同一个东西。

对着宿主抄的是**结构与版式**，色值一律换成库的语气令牌。因此有四处的取值与宿主
**不一样**——都是有意的，不是抄漏：

| | 宿主那条 toast | 本库 `TMessage` | 为什么 |
| --- | --- | --- | --- |
| `info` 的色相 | 蓝（`#1d4ed8` 那支 Tailwind 字面量） | 中性灰（`--73-info`） | 本库的 `info` 是登记过的中性色，也与 Element 的 `info` 同族 |
| 描边透明度 | 50% | `--73-*-line` 的 32% | 与 `--73-accent-line` 同一档，换基色时描边自动跟随 |
| 投影 | 两层纯黑（40% / 30%） | `--73-shadow-panel` | 换主题时投影该跟着变，纯黑不会 |
| 图标 | 无 | 无（刻意不加） | 库的其它语气组件带图标，但提示条要的是「零视觉变化」，一致性让位 |

另有一处**行为上**的差异，不是收敛而是本库既有的规则：宿主固定 2600ms 消失，
本库默认 3000ms 且**随时长自适应**（上限 8000ms，见 `manager.ts` 的 `scheduleClose`）。
要完全对齐就显式传 `duration: 2600`。

关闭按钮的默认值相应从 `false` 改成 `true`（`MessageOptions.closable`）：宿主那条一直
带 `×`，迁移时不该凭空少掉一个出口。

## 六、工程取舍

### 发源码，不发构建产物

与 `tags-wasm` 的模式相同（路径依赖），但**link 的是源码而不是 `pkg/`**。
`tags-wasm` 必须先在 Rust 侧重建 `pkg/` 才能被消费，它的文档里明确记着这个代价。
组件库要边迁移边改，每改一个组件重建一次会把迁移拖慢；link 源码让 HMR 跨包生效。

前提已经具备：`user_client/vite.config.ts` 里本来就有 `server.fs.allow: ['..']`，
dev server 允许提供项目目录外的文件。

代价是**宿主必须能编译 `.vue` 源码**（Vite + `@vitejs/plugin-vue` 本来就有），
以及本库不能用宿主的路径别名——见下条。

### 库内一律用相对路径，不要 `@/`

`user_client` 把 `@` 指向 `user_client/src`。本库是发源码的，库内写 `@/xxx`
在宿主里会被解析到**宿主自己的** src 去：本地 `vue-tsc` 能过，一进宿主就报
「找不到模块」。所以 `tsconfig.app.json` 里**刻意没有** `paths` 映射——
那不是遗漏，是护栏。

### 没有 build 步骤

`package.json` 里没有 `build`，只有 `dev`（起 playground）与 `type-check`。发源码就不需要
构建产物；`sitemap`、`SEO` 那类产物与本库无关。校验入口只有 `pnpm type-check`
（`vue-tsc --build`，会编译 `.vue`、做模板类型检查并生成声明）。

`playground/` 是配套的预览页（`pnpm dev`，端口 5180，`strictPort` 打开），
用来肉眼验证主题与组件，同时它自己也受 `type-check` 覆盖。**它不是发布内容**，
`exports` 里没有任何指向它的路径。`strictPort` 是刻意开的：实测端口被占时 Vite 会
悄悄换一个，结果对着文档里的地址看到的是另一个页面——宁可让它直接报错。

### 没有 pnpm workspace

根目录不是仓库，各子项目各自独立。跨子项目共享只有路径依赖一条路
（`pnpm-workspace.yaml` 里只有 `supportedArchitectures`，没有 `packages:`）。
本库沿用这个既有模式，不去引入 workspace。

### 样式子路径必须带 `.css` 后缀

`ui_73info/styles.css` 而不是 `ui_73info/styles`。宿主的 `env.d.ts` 里只有
`/// <reference types="vite/client" />` 提供的 `declare module '*.css'`，它按后缀匹配。
少写后缀 Vite 能跑，但 `vue-tsc` 会在 `main.ts` 那一行报找不到模块。

## 七、接入前端

本库**先服务 `user_client`**，架构上预留其他三个前端（主题是选择器，不是硬编码的端）。
接入 `user_client` 已经完成（2026-09-30），实际动的地方：

| 位置 | 动作 | 状态 |
| --- | --- | --- |
| `vite.config.ts` 的 `server.fs.allow` | 允许提供 `../ui_73info` 下的文件 | 已有 `['..']`，无需改动 |
| `vite.config.ts` 的 `optimizeDeps.exclude` | 把 `ui_73info` 加进去 | 已加（与 `tags-wasm` 并列） |
| `vite.config.ts` 的 `manualChunks` | 给 `ui_73info` 单独分一块 `ui-73info` | 已加，匹配 `'/ui_73info/'` |
| `package.json` | `"ui_73info": "link:../ui_73info"` | 已加；Windows 上是**符号链接**，改库源码宿主的 HMR 立刻生效（实测过） |
| `main.ts` | 引 `ui_73info/styles.css`（页面样式**之前**） | 已加；迁移期间它排在 `element-plus/dist/index.css` 之后，Element 移除后就在第一位 |
| `router/index.ts` | `beforeEach` 里按路由归属调 `applyTheme` | 已加，判据复用既有的 `isDeveloperRoute` |
| `alias.css` | 旧变量名桥接层 | **刻意没引**（理由见下） |

### 为什么没引 `alias.css`

它的前提是「旧变量名还没换、但值要统一到一处」，而逐页迁移走的是另一条路：
**一页一页直接把该页要改的取值换成 `--73-*`**；页面自己那层的 `--dev-*` / `--portal-*`
（底色、卡片、正文墨色）继续由宿主样式提供。所以全程用不上这个桥。

它的前置条件里还有一条是致命的：不挂主题属性就引入，`--dev-*` 会被解析成门户侧色值、
**开发者页面整片变色**。逐页迁移没有这个风险，因为每页只动自己那几个取值。

**整个文件在迁移完成后应当删除**——迁移已于 2026-10-01 完成，它一次都没被引过。
它只在「所有页面的旧变量名一起换成 `--73-*`」那一步才有意义，那一步是全局的、不是逐页的。

### 主题判据为什么复用 `isDeveloperRoute`

开发者工作台的真实路径是 **`/workbench/developer/*`**（`devWorkbenchRoutes` 挂在
`/workbench` 下），不是 `/dev/*`。只看 `path.startsWith('/dev')` 会把它错判成门户主题。
既有的 `isDeveloperRoute`（`path.startsWith('/dev') || to.matched.some(r => r.meta.devArea)`）
已经把这个坑填过了，直接复用，不另立一条规则——否则迟早两条规则会漂移。

## 八、未实现清单

### 与 Element 的已知差距（有账，不是漏做）

| 未实现 | 为什么，以及现在怎么办 |
| --- | --- |
| `el-select-v2` 的**虚拟化** | `TSelect` 不做虚拟滚动，改为**过滤后最多渲染 `maxVisibleOptions` 项**（默认 200）。起因是实测：渠道银行字典 5260 条交给普通渲染时，打开面板一个 3.7 秒的 long task、DOM 节点 578 → 11259，每敲一个字 1~2 秒。截断只对 `filterable` 生效（不可过滤时截断会让后面的选项永远选不到），被截掉时列表下方提示继续输入；`maxVisibleOptions=0` 可关掉。真要支撑「不可过滤的上万条」仍需虚拟滚动，那套独立子系统仍未做 |
| `ElConfigProvider` | 它做的是「全局尺寸与语言注入」。本库的尺寸走组件的 `size` prop 与 `TForm` 的整表 `size`；**语言没有做层——组件内的固定文案（「请选择」「暂无数据」「加载中」）是中文硬编码**。要国际化得加一个 locale 层，目前没有 |
| 表格的 `sortable` / `type="selection"` / `type="index"` / 展开行 / 树形数据 / `span-method` | user_client 里用量**均为 0**（实测数据见第五节清单的来源），所以没做。要加排序先想清楚「前端排还是后端排」——真实列表页多半要后端排 |
| `v-loading` 指令 | 没有指令层。`TTable` 自带 `loading`（覆盖了那 22 处里的表格用法），其余场景用骨架或自己包一层 |
| `TDatePicker` 的 `shortcuts` 与 `default-time` | 快捷入口（今天 / 本周 / 本月）各端要的不一样，做进组件会把业务口径塞进基础库；`default-time` 对「日期+时间」的默认时刻，现在取当前时分秒或已有值 |
| 组件文案的国际化的日期本地化 | 同上，都在 locale 这一层里，目前没有 |
