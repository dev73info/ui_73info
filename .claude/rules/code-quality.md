# 代码质量与结构约束（组件库 ui_73info）

> 正本：根仓 `.claude/rules/前端标准化.md`。本仓是**四端共用的组件库**，规则与业务仓不同：
> 这里错一次，四个消费方一起错。

## 一、本库的定位与红线

- **零第三方 UI 依赖**：不要为了省事引入 Element Plus / Naive UI 或别的组件库——本库存在的意义就是替换它们。
- **发源码不发构建产物**：`package.json` 的入口指向 `src/`，消费方以 link 依赖吃源码（改完 HMR 立刻生效）。
- **设计令牌的唯一真源**：`src/styles/tokens.css` 里的 `--73-*` 是本库与四个宿主的共同取值来源；
  本库内部也**不许写裸色值**（`#rrggbb` / `rgb()` / `hsl()`），一律 `var(--73-*)`。
- 组件注释与文案一律中文；界面文案纪律见 `.claude/rules/ui-copy.md`。

## 二、破坏性改动的处置

改 **props / 事件 / 插槽 / 样式令牌 / 组件名** 属于破坏性改动：

1. 先确认消费方——目前 `../user_client` 以 `link:../ui_73info` 消费（`../admin_client` 计划中）；
2. 跨仓同名分支一起改，PR 正文互相贴链接；
3. 宿主里跑一次 `pnpm type-check` 与 `pnpm test:ci` 作为联动证据，贴进本仓 PR。

新增可选 props / 新插槽是兼容改动，不受上面限制。

## 三、测试

- 每个组件**至少 1 条交互用例**（Vitest + `@vue/test-utils`），`pnpm test` 必须绿。
- 已知缺陷用 `it.fails()` 钉住（当前 7 条），修好一条就把对应的 `it.fails` 改成 `it`——
  别把 `it.fails` 当通过。
- 新增组件先写用例再补实现。

## 四、结构与可读性

- 本库没有 `check:frontend`，结构约束靠评审：单个 `.vue` 尽量 ≤400 行、单个 `.ts` ≤300 行，超了拆。
- 组件只做展示与交互，**不放业务逻辑与接口调用**；数据由宿主传入。
- 样式一律走令牌与 `:root` 变量，不在组件里硬编码间距档位。

## 五、门禁

`pnpm type-check` + `pnpm test` 必须绿。本库目前**还没有 lint / format / CI 工作流**（已知缺口），
所以格式按仓库既有风格手写，不要引入新的格式化风格。
